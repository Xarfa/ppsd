## 2. 架构

```
浏览器
  │  http://202.195.250.119/PPSD_new/        ← 方案 A（管理员加 4 行后）
  │  http://localhost:8080/PPSD_new/         ← 方案 B（本地 ssh 隧道，无需管理员）
  ▼
Apache（80 端口，root 管理）
  └─ <Location "/PPSD_new">  ──ProxyPass──▶  http://localhost:3618/
                                                │
                                                ▼
                        Node 22（~/node22/bin/node，跑在 wjj 家目录）
                        └─ ~/ppsd-26/app/backend/src/server.js
                             ├─ 页面：~/ppsd-26/app/dist（同一进程托管）
                             └─ 接口：/api/*  →  pglite（~/ppsd-26/app/pgdata）
```

**单进程同时提供页面和接口** —— 所以 Apache 侧只需要一段 `Location`，
不用建 web 目录、不用把前端文件放进 `/home/www/html/`。

## 3. 关键约束（都是实测踩出来的）

### 3.1 glibc：必须用 unofficial-builds 的 glibc-217 版

| 事实 | 值 |
|---|---|
| 服务器系统 | Ubuntu 16.04.7 LTS |
| 系统 glibc | **2.23** |
| Node 官方二进制要求 | glibc ≥ **2.28**（Node 18 起） |
| 实测结果 | 官方 `node-v22.23.3-linux-x64.tar.xz` 运行即报 `GLIBC_2.28 not found` |

**解法**：用 Node 官方团队维护的 unofficial-builds 里带 `glibc-217` 标记的包 ——
同版本号、同源码，只是针对老 glibc 重新编译：

```
https://unofficial-builds.nodejs.org/download/release/v22.23.3/node-v22.23.3-linux-x64-glibc-217.tar.gz
```

已装到 `~/node22`，`~/node22/bin/node -v` → `v22.23.3`，
WASM / ESM / `process.loadEnvFile` / `structuredClone` 全部可用（已逐项验证）。

> 注意：`~/node22/bin/npm` 的 shebang 是 `#!/usr/bin/env node`，如果不先把
> `~/node22/bin` 放进 PATH 最前面，npm 会被系统 Node 14 启动而报错。
> **本项目的部署与运行都不依赖 npm**，直接 `node src/db/load.js` / `node src/server.js`。

### 3.2 数据量：不要相信 Windows 上的 `du`

`du -sh backend` 在 NTFS 上报 **1.1 G**，但 `find -type f -printf '%s'` 求和只有 **27 M**
（1055 个文件，NTFS 簇分配导致虚高）。真实上传量就是这个量级，
之前的部署报告按 1.1G 估算传输时间，是错的。

### 3.3 端口探测：非 80 端口从外面不可达

从校外/VPN 侧对 202.195.250.119 做 TCP 连接测试时，**随机端口也显示"通"**
（中间设备无差别接受握手），所以裸 TCP 探测**不可信**；
用 HTTP 请求判断才是准的：`curl http://202.195.250.119:3615/` 超时 → 非 80 端口不通。

结论：**只能靠 Apache 80 端口反代**（或本地 SSH 隧道）。别指望内网直连 3618。

### 3.4 `pkill -f "node src/server.js"` 会杀掉自己

`pkill -f` 匹配完整命令行，而这条命令自身的命令行里也含 `node src/server.js`，
在 ssh 一行式命令里执行时会把发起命令的 shell 一起杀掉（ssh 会话直接断）。
脚本里统一用方括号写法规避：`pkill -f "[n]ode src/server.js"`。

### 3.5 Windows 本地测试的坑（不影响服务器）

Git Bash 的 `pkill` 杀不动 Windows 原生 `node.exe`，本地验证改代码后必须用
`taskkill //PID <pid> //F`，否则老进程占着端口、新代码不生效（会看到自相矛盾的测试结果）。

### 3.6 前端 base 与后端路径必须对齐

前端按 `base=/PPSD_new/` 构建（`vite.config.server.mjs`），资源引用和 API 请求都带前缀。
后端 `src/server.js` 为此做了兼容（**同一份产物两种访问方式都能用**）：

```js
app.use('/PPSD_new', express.static(distDir));   // 直连端口（方案 B / 内网直连）
app.use(express.static(distDir));                // Apache 反代（ProxyPass 已剥前缀）
const API_PREFIXES = ['/api', '/PPSD_new/api'];  // 接口同样挂两组
```

## 5. 三种访问方式

### 方案 A（正式）：`http://202.195.250.119/PPSD_new/`

**前提**：管理员在 `/etc/apache2/sites-enabled/000-default.conf` 的 `</VirtualHost>` 前新增：

```apache
<Location "/PPSD_new">
    ProxyPreserveHost On
    ProxyPass http://localhost:3618/
    ProxyPassReverse http://localhost:3618/
</Location>
```

然后 `apachectl graceful`。**不建目录、不改权限、不影响其他任何站点**。

验证（服务器上）：`curl -s http://202.195.250.119/PPSD_new/api/health`

### 方案 B（保底，无需管理员）：SSH 隧道

```powershell
ssh -L 8080:localhost:3618 lab-hj      # 演示电脑上执行，窗口保持打开
```
浏览器打开 `http://localhost:8080/PPSD_new/`。

**已实测**：服务器 sshd 允许端口转发（用 80 端口做过对照测试，返回 Apache 真实响应）。
适合"管理员没到位"时给导师演示 —— 页面、接口、数据库全都是服务器上那套真的。

### 方案 C（应急降级）：静态单文件

`dist-demo/index.html`（内嵌 165 位点快照，hash 路由）放到任一个 80 端口可达的目录。
**会借用别人的目录**（如 `/home/www/html/RiceSALTnet/`，777 可写），非必要不用。

## 7. 日常维护

| 场景 | 操作 |
|---|---|
| 重启后端 | `bash ~/ppsd-26/app/restart.sh` |
| 停止后端 | `bash ~/ppsd-26/app/stop.sh` |
| 看日志 | `tail -f ~/ppsd-26/app/backend.log` |
| 服务器重启后拉起 | `nohup bash ~/ppsd-26/app/start.sh > ~/ppsd-26/app/backend.log 2>&1 &` |
| 只改前端 | 本地 `npm run build:server` → 重新打 `ppsd-dist.tar.gz` → 上传 → 解压覆盖 `~/ppsd-26/app/dist`（**不用重启后端**，静态文件是实时读的） |
| 只改后端 | 重打 `ppsd-backend.tar.gz` → 上传 → 解压 → `bash ~/ppsd-26/app/restart.sh` |
| 数据更新 | 重打 `ppsd-data.tar.gz` → 上传 → 解压 → `node src/db/load.js`（重灌） |
| 开机自启（可选） | `crontab -e` 加一行 `@reboot /home/riceUsers/wjj/PPSD/start.sh`（需脚本内重定向日志） |
